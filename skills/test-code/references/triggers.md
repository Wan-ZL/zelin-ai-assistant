# Triggers — the second axis (mandatory add-ons regardless of tier)

Adapted from robust-code's hardened layers. `detect.py` scans the **added lines** of the diff versus the merge-base (plus untracked files) with the regexes below and the file-name rules; every fired trigger appends its add-on check to the default selection. The user may deselect an add-on only by waiving it with a reason (`"triggers_waived": {"<trigger>": "<reason>"}`), which the report records as N-A with that reason. A fired trigger whose add-on finds no matching test file is a **FAIL** (`missing`): write the test or waive it visibly.

Test-subset matching is by file name under the project's tests directory (`tests/`, `test/`, `spec/`), case-insensitive, Python only in v1; a JS-only project gets `unavailable` for these add-ons.

## Reading the evidence

`detect.json → triggers[]` carries up to eight `evidence` lines per trigger (`path:line: snippet`) and the total hit count. The tier recommendation escalates to 档 4 when `persisted_state`, `concurrency` or `persisted_format` fired or a constitution module (`qa/mutation_targets.toml`) changed, and to 档 3 when `boundary` or `deps_changed` fired or more than 15 files changed. Docs-only diffs recommend 档 1; an empty diff recommends 档 2 on the whole tree.

## Writing the missing test (when an add-on is `missing`)

Put the file under the tests directory with the trigger word in its name (e.g. `tests/test_<module>_crash_recovery.py`), make it deterministic (inject the fault, do not sleep), assert the documented behaviour, watch it fail once against a broken implementation, then rerun the ladder with the same selection. Do not waive to get green — waivers are for genuinely inapplicable cases (a read-only refactor that touched a `sqlite3` import line, for instance).
