- **通知偏好：安静时段 + 分类开关（issue #29，CONTRACT §28 2026-09-12 追记）**：设置 → 通知区多了六把旋钮——「新提案通知」「任务停下来时通知」「失败通知」三把分类开关（**都默认开**，新装机行为一字不变）与「安静时段」开关 + 起止时间（默认 22:00 → 08:00，关着）。安静时段里除失败类外一律不弹横幅；**失败通知穿透安静时段**（凭证半夜过期、雷达停摆还是要当场知道），要静音它得在这里显式关掉。**诚实注**：issue 提的「压到早上再弹」没做，也做不了——§28 的通知队列只留 10 分钟（stale 清扫），被压住的条目会先老死，「攒一夜」在这套机制下是谎话。所以安静时段是**写方不入队**：`act/lib/notify.notify` 在写队列文件之前判一次偏好，被吞的通知根本不产生队列条目。因此 §28 已有的 stale 600 s / burst 5 / 消费即删 / `review_notify` 三档一个字没动，壳的 `NotifyRelay.swift` 也仍是 `mac/` 冻结件的逐字副本；职责自此切分成「抑制归写方（Python）、呈现（横幅 / 声音）归消费方（壳）」，顺带让非 darwin 的 notify-send 路径也吃到同一套偏好。完成提醒不另立第二把开关——`review_notify` 三档（关 / 横幅 / 横幅+声音）仍是它唯一的旋钮。队列条目的 `kind` 词表随之补齐 `proposal` / `needs_input` / `failure` 三个（add-only，同 PR 登记进 `server/notify_catalog.py`），守护进程的每条通知都打上了它的类。起止时间走 §70 同一个 HH:MM 词法（目录 `check` 词表 add-only 新增 `clock_time`，设置页保存前按同一条规则拦、坏值 400 且不落盘，好值过闸后归一再落盘——`9:30` 存成 `09:30`；空串仍是清键）；任一端配错、零长窗或读配置出意外一律 fail-open（照发——丢一条通知比吞一条通知贵）。`scripts/auto-deploy.sh` 的每条告警（回滚失败 / 被拒、已回滚、CI 红、全盘访问被挡、安装未完成、无法验 CI、工作树脏、无法 fast-forward）都打上 `failure` 因而穿透安静时段，两条部署成功行不打——夜里不该为一次顺利升级弹横幅。失败类被自己的开关静音时 §48 的两道巡检照跑（僵尸 health 清理、恢复出账、无基线台账都在里面），只是不花 anti-nag 台账：开关翻回来的那一 pass 就重报。诚实注二：每日自我改进循环出厂就在 03:30 跑，正落在出厂安静窗（22:00 → 08:00）内——设置页的文案直说这件事。**你按下的按钮一定会回话**：设置 · 每周摘要「现在生成一份」的三条回执（已生成 / 没有数据 / 生成失败）打第五个 kind `receipt`——没有分类开关、也不受安静时段管。那次运行是分离的，按钮自己的回执句写着「完成后会弹通知」，而失败那条路上一张卡都不铸：半夜十点半按一下却被安静时段吃掉，人只会以为按钮坏了。同一模块**排定**的那次成功通知仍受安静时段管（凌晨没人在等它）。
