二、根因：一枚用真时钟盖的戳，把 14 天窗口越量越短

失败的判例是 tests/test_review_stale_sweep.py:203 test_the_window_restarts_from_the_restore_not_from_the_old_stamp， 报 AssertionError: Lists differ: [] != ['P-1']。链条如下：

  1. 判例存一张 30 天没动的待验收卡，self.sweep() 把它归档进回收站；
  2. registry.restore() 把它捞回来，用真时钟盖 execution.restored_at；
  3. restored_at 在 maintenance._EXECUTION_STAMPS 里（f8a734d1 加的：捞回来算 owner 活动），于是 last_activity() 返回这枚真时钟戳；
  4. _idle_days(req, today) 用 today = NOW + 15d = 2026-09-30 减它；
  5. 闸门是 idle ≥ review_stale_days（出厂 14）。真日期 09-16 时 idle=14 刚好过；09-17 时 idle=13，闸门关，通知列表变空，断言 [] != ['P-1']。

⭐ 这个判例出生就在一个三天的窗口里。 我把 ad4f0b71 在隔离树里 回滚掉，再平移真时钟逐天重跑，量出了引信的两端：

wall clock 2026-09-12  FAILED        wall clock 2026-09-16  OK
wall clock 2026-09-13  FAILED        wall clock 2026-09-17  FAILED   <-- #405 那次红跑
wall clock 2026-09-14  OK            wall clock 2026-09-18  FAILED
wall clock 2026-09-15  OK            wall clock 2026-09-19  FAILED

它由 f8a734d1 在 2026-09-15 写下，而能让它通过的真实日期只有 09-14 / 09-15 / 09-16。换句话说：写下它的那一天，引信已经点着了，只剩两天。 两个方向都会炸——真日期 ≥ 09-17 时第 203 行报 [] != ['P-1']； ≤ 09-13 时第 202 行反过来报 ['P-1'] != []（那时旧戳比 restored_at 新， _notice_state 返回 "set"，反而在 20 小时闸门上重新归档）。

⚠️ 三条失败全是假报：patched Python 时钟 vs 没被 patch 的文件系统 mtime

我的 harness 换掉了 datetime.date / datetime.datetime， 但换不掉文件系统的时钟。任何「拿 Python 的 now 去减 st_mtime」的判例 都会因此假红。三条逐一查实：

  • test_card_lifecycle.ArchiveStaleTestCase.test_daily_gate_prevents_second_sweep —— housekeeping.py:68 的 24 小时闸门算 age = datetime.now(utc).timestamp() − marker.stat().st_mtime。 实测：只平移 Python 时钟时 age = 86400.00s ⇒ age < 86400 为假 ⇒ 闸门开 ⇒ 二次清扫跑了； 把两个时钟一起平移（真机上的实际情形）则 age = 0.00s、闸门照常关。
  • test_honest_receipts.DigestFailureNotifyTestCase 两条 —— weekly_digest.py:132-148 按 mtime（不是文件名里的日期）筛 7 天窗口。 可falsify的预测 + 实测吻合：假报应当只在平移 > WINDOW_DAYS(7) 时出现—— 实测 +0 / +6 天 OK，+7 / +8 / +14 天 FAILED， 拐点正好落在 7。真机上那份 note 的 mtime 会跟着时钟走，永远是「刚写的」。

附带反证：如果肇因是文件名里的 2026-07-15，shift=0 档也该红 （按文件名它今天已经 65 天大了），但它是绿的 ⇒ 判据确实是 mtime。

这项证据是有界的，别当成「全绿保证」

全套件 × 多个平移日期的版本没跑完：本机同时有其他 agent 在跑同一套套件， tests/integration/test_auto_deploy_script.py 那批真 subprocess 判例把几个并发套件 拖到 8 分钟只推进 2.5 秒 CPU，我主动杀掉了。所以最终跑的是 restore / reraise / 老化家族 15 个模块 × 6 个时钟（0 / +1 / +14 / +90 / +365 / +1095 天）， 不是全套件。

① §56.6 的 auto-update 从来没真正推过一根分支 —— 这才是这张卡存在的原因

.github/workflows/update-pr-branches.yml 的本职是把 main 合进每个落后的同仓 PR， 让它们自动接上刚落地的修复。它一次都没做到：缺 secret PR_AUTOUPDATE_TOKEN 时（workflow 头部第 20/26 行自己写明）整条逻辑退化成 report-only，只打印「本来会更新谁」。

09-17 20:41Z 那次 run（35272277210，紧跟在 ad4f0b71 落地之后）的渲染输出原话：

#405: behind by 59 — would update (report-only, no token)
#404: behind by 59 — would update (report-only, no token)
#403: behind by 59 — would update (report-only, no token)

修复已经在 main 上躺了两个小时，workflow 看见 #405 落后 59 个 commit、知道该更新它， 然后什么也没做。#405 就这样又带着过期 merge base 挂了 16 小时，直到 dependabot 自己 在 09-18 12:39Z 合了一次 main。同一颗炸弹因此扇出了多张 pr_red 卡 （#403 / #404 / #405 当时是同一批）。

该 workflow 共 126 次 run，全部 success——它在什么都不做的时候也是绿的， 所以这个空转从来没有报警。修它 = 建一个 fine-grained PAT 并加成 secret， 不需要改代码；但 .github/workflows/ 是 protected path， 且加 secret 只有 owner 能做，所以本轮只报不动。

⚠️ 查证陷阱：这条 workflow 的 run 脚本会被 Actions 逐字回显到日志里， 所以 grep "report-only: PR_AUTOUPDATE_TOKEN is not configured" 一定命中——那是源码回显 （行首带 ANSI [36;1m 追踪前缀），不是证据。唯一可信的是 note 函数吐出的「渲染后」那三行 behind by N — would update。

③ test_auto_deploy_script.py 的预算计时器算错了对象（14 个模块里唯一一个）

tearDownModule（420–424 行）在 time.monotonic() − _T0 > BUDGET_SECONDS 时直接 AssertionError。 而 _T0 = time.monotonic() 在模块作用域（130 行）、 且该文件没有 setUpModule 去重置它——于是计时从 discovery-import 那一刻就开始跑，把在它之前跑的别的模块的耗时也记到自己账上。

我逐个数过：tests/integration/ 里用 _T0 的 14 个模块， 13 个都在 setUpModule 里重置，只有它没有。

NO-RESET test_auto_deploy_script.py      <-- 唯一一个

后果：那个常数自己的注释（600 # 94 runs of real bash+git…，即「预算跟着本模块判例条数走」） 是假的——它其实会被「任何一个排在它前面的新模块」重新上膛。 09-16 01:20Z 炸过一次（took 457s > 420s budget，macOS ci leg）， 提额的 c31cc506 晚了 17 分钟落地；那 457 秒也不是这个模块的开销。

一行就能修：照 13 个兄弟的写法加 setUpModule 重置 _T0。 方向是安全的（只会让 elapsed 变小），而且能让 600 这个数第一次有意义。

⚠️ 我先前的草稿在这条上写错了四处，已按逐条复核改正： 它不是日历炸弹（读的是 time.monotonic() 的流逝时间， 与日期 / NTP / DST 全无关，也无法用平移日期复现）——正确定性是 「慢 runner + 套件增长」型 flake；它不在 #405 那个炸弹的同一个模块里 （那是 tests/test_review_stale_sweep.py）；常数被抬过的是 五次（120→180→240→300→420→600），不是三次；而且它不确定性地只在 macOS leg 上炸—— 同一次 run 里两条 ubuntu leg（409 s / 355 s）都是绿的。

七、方法论备注（下一个 session 可以直接抄）

  • 先看 PR 改了什么，再看红的是什么。 #405 只动了 web/package.json + lockfile，红的却是三个 Python 门——这个错位本身就说明 「根因不在这个 PR 里」，直接把方向从「修 dependabot」扳到「查 main 的历史」。
  • PR 的红跑要和 merge base 一起读。 红跑时刻（08:37Z）比修复落地（18:37Z）早 10 小时， 对照 main 同期全绿 —— 「过期 merge base」一眼就成立， 而 gh pr checks 当时显示 pending（rebase 后的新跑），差点被误读成「还在红」。
  • 自己的假设要自己去证伪。 我一开始判定 180 行那条判例是「空过的」（vacuous）， 于是去隔离树里做变异：把 restored_at 从 _EXECUTION_STAMPS 里删掉—— 判例照样被杀死，假设被我自己的实验推翻。改完之后又复跑同一个变异体确认 杀伤力没有下降（同样 2 红）。「这个判例其实没在测东西」是个很好用但很容易错的直觉， 别不做变异就下结论。
  • 变异实验住在隔离树里。 git archive HEAD | tar -x -C <tmp> 比「改完记得改回来」安全得多，尤其当还有并发的 agent 在读同一个工作树。 代价是那棵树没有 .git，所以必须配一个 shift=0 对照档。
  • 平移挂钟的正确姿势。 Homebrew 的 Python 自带 sitecustomize.py， 会盖掉你放在 cwd 的同名文件（实测无效）；改用一个显式 runner，在 import unittest 之前替换 datetime.date / datetime.datetime。 只有 import datetime as _dt + 延迟读取的模块能被覆盖到； from datetime import datetime 那种在 import 期就绑死了，覆盖不到。
  • unittest 的进度点是不带换行的，重定向到文件时会一直卡在缓冲区里—— 日志「不长」不等于进程没在动，要看 ps -o time 的 CPU 时间。 本机 CPU 才 2.5 秒而 elapsed 8 分钟 = 它在等 subprocess，不是在算。
