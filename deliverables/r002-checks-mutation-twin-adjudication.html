2 · 判决的地基：三件先验事实

  1. checks.py 在 main / R-301 / R-217 上逐字节相同（blob 669cacb6c5c1，sha256 322d706b… == 夜报 state 的 content_hash）； 三份原映射判例也逐字节相同。⇒ 404 体的 site_id 清单三分支直接可比，行号不用重算。
  2. 加测试不会让已死的位点复活 ⇒ 只需判那 404 个存活体，不必重跑全部 839。
  3. 两个分支都没改 checks.py、没改任何既有判例 —— 但为与夜报口径完全一致， 本轮仍按各分支的完整映射集跑（#401 九份 / #391 八份）。

踩到一个 zsh 坑，差点据此下错结论

git show "$r:path" 里 zsh 会把 :s… 当成 history modifier 施加到 $r 上，path 被整段吞掉，git show 转而打印 commit 本体（283 字节）。 于是三个分支的 checks.py 看起来哈希全不一样 —— 我差点据此判定「两个孪生是在旧版 checks.py 上做的、结论不可比」。正确写法是把冒号放在两个引号之间、落在参数展开之外：

git show "$r":"skills/test-code/scripts/checks.py" | shasum -a 256

5 · 分歧那三个位点，谁对

line 28（#401 独杀）—— #401 对，#391 判错了 已复核到具体判例

#391 的 PR 正文把它归成等价体，理由是「The scripts dir is already sys.path[0] for every real entry point … The index only changes shadowing priority against paths that never carry these module names」。

#401 的 tests/test_skill_test_code_plan_plumbing.py::test_skill_scripts_dir_is_prepended_not_inserted_later 直接反驳了这个前提：test-code skill 是跑在任意用户 repo 里的，那些 repo 完全可能自带叫 complexity_min / ladder_common / structure_check 的模块， 所以「插在 0 位」是成文契约而不是巧合。观测法是先把一个竞争目录塞到 sys.path[0]、 reload 模块级代码、断言 skill 目录把它顶掉；期望值取自 tests/skill_test_code_testkit.py 里独立算出的 kit.SKILL_SCRIPTS， 不是从 checks.py 抄的。

我把这个变异体对 #401 的九份映射文件逐份单独跑确认杀它的就是这一份判例， 不是别处的偶然副作用：

KILLS   baseline=pass  mutant=fail   tests/test_skill_test_code_plan_plumbing.py
survives  ... 其余八份全部 mutant=pass

line 438（#391 独杀）—— 两边都站得住，#391 更严，但不值一次合车

#401 用机器对拍判它等价：唯一消费点是 checks.py:447 if match and _unpinned(...)， 布尔语境下 None 与 False 不可分；392 条 uses: 语料上 bool() / _pin_violations / 整个 check_actions_sha_pin 的结果 IDENTICAL。

#391 不反驳这个事实 —— 它的 docstring 明确承认「豁免分支的返回值只在真假位置被消费」， 然后选定一条更强的不变量（「谓词只返真布尔」）用 assertIs 钉住。 两种立场都成文、都诚实；差别是「钉产品行为」还是「钉声明的返回类型」。

这是唯一值得从败者身上嫁接的东西，量级约两条断言 —— 合完 #401 之后的两行 follow-up， 不必为它承担一次冲突合车。

9 · 带过来的三处待拍板缺陷

这三处是 #401 在补判例时查出来的，本轮一个没碰 —— 判例钉的是今天的行为， 修任何一条都会故意把相应断言变红，所以要连着改。诊断全文在 #401 的 docs/design/progress/2026-09-16-self-improve-r301-checks-mutation-kills.md。

① 缺工具被报成项目失败（三处）真缺陷

_e2e_for_pkg（npm run test:e2e）、_b_perf_budget （npm run bench）、_b_bundle_size（npm run size）只查 package.json 里有没有那个 script，不查 npm 在不在 PATH； 而同一个文件里的 _npm_audit_steps 查了 —— 所以这是不一致，不是取舍。 后果：没装 node/npm 的机器上这三层把必然 ENOENT 的命令交给 runner，记成 RED（项目坏了）而不是 UNAVAILABLE（工具没装），破的是 skill 的头号契约 —— 报告里那个三分「not run」划分。一行修法：照 _npm_audit_steps 加 _tool(ctx, "npm") 闸门。

② docs_drift 的目录级 .gitignore 条目不做前缀匹配真缺陷

_ignored_literals 特意把 build/ 的斜杠剥掉收成字面量 "build"， 但 dangling 只比整条路径和 basename、从不比路径前缀 —— 那个 .rstrip("/") 对每个目录条目都是白做的。后果：gitignore 掉构建输出目录、 又在文档里提到里面某个文件的仓库，docs_drift 假红。

③ _span_cov 无数据时 fail-open设计问题，请拍板

函数区间内一条 coverage 数据都没有时返回 1.0，于是没被插桩的函数拿到最好的 CRAP 分（CC=6 → 6.0 过门；按全未覆盖算是 42.0 会红）。这是 fail-open， 而模块 docstring 写的是「自制检查一律 fail closed」。很可能是故意的（避免对没插桩的文件假红）。 请定：「没有行数据」该算 cov=0.0、进 errors、 还是保持现状并给 docstring 加个例外。
