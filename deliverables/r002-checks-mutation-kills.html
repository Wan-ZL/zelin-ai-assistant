四个 PR 的 toml 改动都落在 qa/mutation_targets.toml:93 同一行，所以合掉任意一个，其余三个必然文本冲突。这其实是好事：它保证不会有人把两份重复的判例一起合进去。

三 · 两个 lane 缺陷

1. 同题卡被并发扇出到六个 session

本轮 ListAgents 看到除本 session 外，还有 R-002、R-001、R-8153 ×2 四个 session 挂着同一个「补测试：checks.py 变异存活」标题（连已收工的 R-217 / R-301 共六个）。它们各自独立跑同一套判读、各自开 PR，算力与 token 乘六。

副作用已经实际发生过：并发期间共享 worktree 的 checks.py 被别的探针留下过未提交的注入变异体，谁在那棵树上 git commit -a 就会把变异体送进生产。本 PR 的树已逐项核过干净（git diff origin/main -- checks.py 空输出，reflog 无外来操作）。

2. 卡号跨发现重复，而 lane 契约按分支名找 PR

另一个 session 拿到的卡也编号 R-002，但内容是完全无关的 web Filters popover Escape 修复。它先占了分支名，于是 ai/self-improve/R-002 现在指向 PR #427（fix(web): close the Filters popover on Escape…，与 #425/R-306 同题）。

lane 契约写的是「分支必须叫 ai/self-improve/R-002，守护进程按它查 PR」。照办只有两条路：非 fast-forward 被拒，或 force-push 覆盖掉别人的工作——后者是破坏性的，契约本身也禁止，所以没做。本 PR 因此开在 ai/self-improve/R-002-checks-mutation 上。

后果需要 owner 知道：守护进程按 ai/self-improve/R-002 去查，会查到 #427，把一个 web 修复当成本卡的交付物。修法在 lane 侧（卡号全局唯一，或分支名带发现指纹），不是能在 PR 里绕过去的事。

剩下 3 个是等价变异体

  • int_plus1@556:30 —— raw.split("#", 1)[0] → maxsplit=2。只有下标 [0] 被消费，而任何 maxsplit ≥ 1 的 [0] 都是第一个分隔符之前那段，变异后的 maxsplit 经 [0] 不可达。

六 · 四条未修的真缺陷

判例钉的是今天的行为，所以修任何一条都会故意把相应断言变红，要一起改。本轮按「只修测试网」的范围一条都没改。

1. 缺工具被报成项目失败 范围从 3 处扩到 10 处

checks.py 里有 十个 kind:"cmd"/"substituted" 的 plan 直接 exec npm/npx 而从不问 _tool(ctx,"npm")，尽管 detect.py:25 明明把两者都探进了 det["tools"]。#401 点名五处：_e2e_for_pkg :998/:1000、_b_perf_budget :1174、_b_bundle_size :1323/:1325；另五处同形（knip / jscpd / api-extractor / license-checker / stryker 只确认 node_modules/.bin 里有 bin，没过 _js_ready 闸门）。

同文件的 _npm_audit_steps（:1128）查了 —— 所以这是不一致，不是取舍。后果：没装 node/npm 的机器上这十层把必然 ENOENT 的命令交给 runner，记成 RED（项目坏了）而不是 UNAVAILABLE（工具没装），破的是 skill 的头号契约（三分「not run」划分）。

一行修法：照 _npm_audit_steps 在这些分支前加 _tool(ctx,"npm") / _js_ready(...) 闸门，不过则 _unavailable("npm not on PATH")。

2. docs_drift 的目录级 .gitignore 条目不豁免目录内文件

_ignored_literals（:552-558）特意 .rstrip("/") 把 build/ 收成字面量 "build"，但 dangling（:570-573）只比整条路径和 basename，从不比路径前缀，那个 rstrip 白做。

本轮复核补两点精度：触发还需另四个条件同时成立（token 首段在 top_dirs 里、扩展名在 _DOC_EXT 内、路径未被 tracked、该顶层目录至少有一个 tracked 文件），所以命中面比听起来窄；另外它只读仓库根的 .gitignore，子目录里的一概不看。

3. _span_cov 无数据时 fail-open 返 1.0 设计问题

_span_cov（:708-713）在函数区间内一条 coverage 数据都没有时返回 1.0，于是 crap_score(cc, 1.0) 塌缩成 cc 本身；在默认 crap_max = 30.0 下，任何 CC ≤ 30 且完全没被测到的函数静默通过。这是 fail-open，而模块 docstring 写的是「自制检查一律 fail closed」。

它很可能是故意的（避免对没插桩的文件假红）。请 owner 定：算 cov=0.0、进 errors、还是保持现状并给 docstring 那句话加个例外。

4. 🔴 本轮新查出：超帽文件被静默跳过，secret_scan 对 CONTRACT.md 失明

lc.read_text（ladder_common.py:200-203）对超过 TEXT_CAP_BYTES（ladder_common.py:34，1 MiB）的文件返回 None；_scan_files（checks.py:376-386）在 if text is not None:（:382）把它丢掉 —— 既不记违例，也不进 errors。而 _finish_scan（:389-393）只看 errors，所以这次跳过从不出现在报告里。

这与 _scan_files 自己的 docstring 直接矛盾：那行写的是「读不到/解析不了记 errors（caller fail closed）」，实际走的是 fail-open 的静默路径。

$ wc -c docs/CONTRACT.md
1513333        # > 1048576 = TEXT_CAP_BYTES

所以本仓库跑第 1 档 secret_scan 时，docs/CONTRACT.md 被整份跳过、零提示。四个消费者同受影响：secret_scan（:426）、actions_sha_pin（:457）、test_smells（:530）、docs_drift（:591）。

一行修法：_scan_files 里把 text is None 归进 errors，让 _finish_scan 按既有 fail-closed 语义报出来；或者提高帽子。请 owner 定哪个。

另有一条轻的：_ctx 在五份判例里有 5 个定义、4 种签名（skills/ 下没有 def _ctx，生产侧的工厂是 checks.py:48 的 make_ctx，五个 helper 都在包它）。这是判例侧的重复，不是生产缺陷。

为什么全套没跑完（不谎报绿）

两次尝试都在跑到第 1 / 第 13 个测试时 exit 144 被系统收割。本轮有六个 session 并发处理同题卡、十几个 agent 同时在跑，load 13–33（18 核）、swap 接近耗尽。

这是资源问题而不是判例问题，证据：同一台机器上把并发降下来之后，定向子集同样 217 条测试全绿，只是墙钟从 0.23 s 劣化到 139 s。

判决看 PR 上的 Tests on ubuntu (Python 3.9 / 3.x) 两条腿。参考：#401 在安静机器上跑过同一套，报 Ran 7814 tests, exit 0；本 PR 的判例字节与它逐字节相同。

一条被驳倒的复核 finding，值得记一笔

复核者提过「定向子集 139 s 超过 per_mutant_timeout_seconds = 60，而 mutate.py 把超时记成杀伤 ⇒ 99.6% 是超时喂出来的虚高」。已被实测否掉：本轮 report.json 的 timeout = 0、error = 0，836 个杀伤里没有一个来自超时。安静机器上子集 0.23 s，对 60 s 有 260 倍余量，夜报又跑在专用 ubuntu runner 上。

这条留在这里是因为它本来是个好怀疑：如果哪天夜报在负载高的机器上跑，超时确实会把分数喂虚。timeout / error 两列要单独看，别只看 score。
