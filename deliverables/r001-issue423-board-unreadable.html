1. 病灶与复现

issue 里的症状是：GET /api/board 起跑后 3 小时翻成 404 dashboard.json not found，而 state/dashboard.json 就在那里（425 KB、 -rw-r--r-- zelin:staff、无 ACL / xattr），同一个解释器在终端里读得动； launchctl kickstart -k 能修，到下次再翻。

代码里的原因只有八行：

def board_bytes(home: Path) -> bytes:
    p = paths.dashboard_path(home)
    try:
        return p.read_bytes()
    except OSError:                     # ← 一切读失败，一个出口
        raise NotFoundError("dashboard.json not found — is actd (or the demo "
                            "seeder) pointed at this AIASSISTANT_HOME?",
                            {"path": str(p)})

为了不靠读代码猜，本轮先写了一份复现脚本，在同一个 HOME 上对照「文件在但 mode 000」 与「文件真的删掉」两种情况：

--- file present, mode 000 (EACCES for a non-root user) ---
exists: True  mode: 0o0
board_bytes -> 404 NOT_FOUND | dashboard.json not found — is actd … ? | {'path': '…/state/dashboard.json'}
health dashboard block: None  verdict: stale

--- file genuinely absent ---
board_bytes -> 404 NOT_FOUND | dashboard.json not found — is actd … ? | {'path': '…/state/dashboard.json'}
health dashboard block: None  verdict: stale

VERDICT: the two cases above are INDISTINGUISHABLE to every client.
⭐ 本轮最值钱的一条发现：§54.2 的日志噪音闸（2026-09-14）把那 1549 行一模一样的 /api/board 404 当噪音整类收编，事后看那是对的—— 但被它压住的那条消息本身是假的。闸没错；错的是没人让真正的 errno 落过盘。 所以本轮除了分类，还补了一条带 errno 的诊断行：下次翻掉，日志里就有那个数字。

四处改动

  1. board_bytes 分类。分界线是 FileNotFoundError vs OSError，不是 PermissionError——本机实测 EPERM(1) / EACCES(13) 是 PermissionError 而 EIO(5) / ELOOP(62) / ENAMETOOLONG(63) 是裸 OSError， 按 PermissionError 分会把 I/O 错误漏回 404。
  2. /api/health 加 add-only 顶层键 dashboard_error = {path, errno, strerror} 或 null。dashboard: null 的含义一字不变， verdict 词表仍是五枚。_dashboard_view 改收已读好的 body，好让那个文件 每次 /api/health 仍然只读一次（判例钉住 read 次数 == 1）。
  3. errno 落一份到日志：_send_api_error 对 details 带 errno 的受控错误多写一行 <CODE> errno=<n> <strerror> path=<…>， 经 Handler.log_message（§54.2 的唯一 stderr 写者）与一个独立的 _PollSampler 实例（同一个类、同一条 300 s 窗）。
  4. 客户端第四态 boardUnreadable：无快照 → AppShell 整页态， 有快照 → ErrorBanner 第三个 warning 变体（快照不清）。向导终章「首份数据」 行报 errno 并撤掉「立即生成一次」。设置页诊断区多两个字段。

3. 六个被 review 打回来才定的取舍

先出了一版实现计划，再让四个对抗 reviewer（法条 / CI 会不会绿 / 用户看到的是不是真话 / 边界 情形）逐条去推翻它。下面六条全是被推翻之后改的。

① dashboard_error 取顶层新键，不加第六个 verdict原方案被否

加 verdict 会静默失效：PipelineBanner.describeHealth 的 default: return null 让新 verdict 一个横幅都不渲染（比今天更差）， repairActd.isRecovered（verdict === "ok" || "unknown"）还会把每次一键修复 都报成 15 s 超时，而 types.ts 把 verdict 声明成 | string、tsc 一个都拦不住。 塞进 dashboard 块要让 _dashboard_view 在读被拒时返非 null，那会翻转 _verdict 并把向导「首份数据」行从红翻成绿色的谎话。

② PipelineBanner 刻意不长 dashboard_error 分支原方案被否

它和看板页的新面同源，两条 role="alert" 说同一句话正是 §47.4 读者 3 与 ErrorBanner 组件头注都明令禁止的「同一信息绝不双份」；插在 verdict switch 之前 还会盖掉 stalled / failing 这两条更急的真话。只改一处：stale 正文里 dashboard == null 此前一律说「看板从未生成」——读被拒时那是假话。判例把 stalled + dashboard_error 仍说「卡住了」钉死。

③ 判据不写成裸 status === 503

本面另一枚 503 是 §68.7 的 SHELL_UNAVAILABLE，把「壳没在跑」说成「看板读不动」 是同一类谎话。判据 = 503 ∧ (BOARD_UNREADABLE ∨ REQUEST_FAILED)，后者覆盖 envelope 体 自己都解不出来时的退化码。判例带一条 SHELL_UNAVAILABLE 反例。

④ 不落 boardError

它的读者全把它读成「离线」——落进去等于对着一台刚答过话的 server 说「连不上本地服务」， 还会把 PipelineBanner / DiagnosticsStrip / MaintenanceBanner / SelfImproveBanner 四条横幅一并关掉（§49 追记 2026-09-05 为同一理由否决过一次）。

⑤ 新面绝不复用 BoardMissingState数据丢失风险

它给的「立即生成一次」会 POST /api/setup/seed-dashboard → write_dashboard 原子替换 dashboard.json，而 registry.load_all 对读不动的卡片文件是静默跳过——在一台只是读不动的机器上那是拿一份可能零卡的 看板盖掉最后一份好快照。这颗按钮此前正对着 owner 出现在向导那一页上。

⑥ 两条差点自己造出 500 的坑第一版实现有

  • UnicodeDecodeError 是 ValueError 而不是 OSError，必须与 json.loads 共用同一个 try。第一版把 except ValueError 只挂在 json.loads 上，一份非 UTF-8 的 dashboard.json 就会让 snapshot() 抛出去、/api/health 变成 500 + 一份栈。
  • _send_api_error 是从 _dispatch 的 except ApiError 子句里调的，从那里抛出去的异常同级 except Exception 兜不住，会逃到 handle_one_request——客户端连 envelope 都收不到。 所以诊断行整段包 try/except，判例直接注入一个会抛的 _errno_diagnostic 证明 envelope 照发。

壳冷启动那一路仍说假话，本 PR 没修

shell/Sources/main.swift 的探活只认 2xx（(200...299).contains(code)）， 503 与今天的 404 一样走 10 s 超时后的「连不上看板服务」启动失败页，上面三条修法全是 launchd 的。 只有窗口已经开着时翻掉（issue 时间线里 16:44 那一次）才走得到本 PR 的新面。 §54.2 的后续，未开卡。

「为什么会被重定向到向导」没修，而且机理与我一开始的猜测不同

server/setup.py 用的是 Path.is_file()，它不吞 EACCES—— 本机实测 mode-000 目录里的文件 is_file() 直接抛 PermissionError(13)， 所以 stat 级拒绝下 /api/setup 自己就是 500 + 一份栈； open 级拒绝下 config.yaml 与 setup_done.json 反而读成「在」， needed: true 只经 secrets_store.read_value 的 except OSError: return None 出现。同一病灶的兄弟，另开一张卡。 向导终章那一行本 PR 已按 §47.4 追记说实话并撤掉播种按钮。

其余明确不做

  • errno 的 OS 层根因（issue 第 3 项）。owner 侧那个只读诊断 job （com.zelin.diag-read）会在下次翻掉时记下 errno；本 PR 只保证那个数字到得了人眼前 ——envelope、/api/health、设置页诊断区、server 日志四处。
  • health._age 的 stat 拒绝（心跳文件）：另一条读者、另一个键，不在 issue 范围。
  • 不动 _read_json（心跳与 loop_health 共用它）、不动 _verdict 的三入参、 不给 503 加 Retry-After（客户端只重试抛错的 fetch，503 不在其列）。

7. 需要 owner 拍板：一个 PR，三张卡
