**owner 要什么**：「我觉得 proposals 这一列不需要了，自动生成任务推进的卡片都放在『潜在任务』中」（2026-09-26）。一句话的设计：`card_sent`（提案）**折叠进** `detected`（潜在任务）——每一条原本把卡落在 `card_sent` 的写路径改落 `detected`，提案列从看板上消失，潜在任务列长出完整的提案卡面，owner 在**同一张卡**上点一次「促成运行」，`detected → approved` 直接开跑。中间那一跳没了，canonical 状态机自此是 `detected → approved → executing → review → delivered`，任意态 → `trashed`。

**什么退役了**：提案列（`<Lane>` + 它的 `LaneComposer` + `ProposalsTriageButton`）、`needs_approval[]` 分区（键与 `counts.needs_approval` 按 add-only 全部留着，恒 `[]` / 恒 `0`，Swift `Contract.swift` / `BoardLane.allCases` 一个字节没动）、§34bis 的「提案积压清理」按钮与 `preset` 值、§51 的第一条 lane（hand 卡免批自动派发）、§10 的 `defer`（暂缓）入口。`card_sent` 这个**值本身不删**——它降为退役但合法的路标：常量留着、store2 的 status CHECK 词表与既有 `transition_whitelist` 行留着、存量卡与迟到的 inbox 重放照旧被正确处置，只是**没有任何生产者再写它**（逐条点名的产地表 = §78.3，不是「凡是 card_sent 都改」这种口号：漏一个，那类卡就出生在一条没有面的车道上、owner 永远看不见，而 CI 全绿）。`dashboard._SIMPLE_LANES` 把 `State.CARD_SENT` 映进 `("debt", _backlog_row)` 的 straggler 分支在归并扫描（§78.5）跑完之后恒不命中，但**永远留着**——「状态还在、面没了」是宪法第 3 条不能接受的形态。

**D80 拍了什么**（全表 §78.2，D80.1–D80.15，实施时不再讨论）：`needs_approval` 的 wire key 活着但恒空（D80.1）；机器卡一律进 `debt[]` 的潜在任务列（D80.2），这条折叠侧条自此默认**展开**（D80.3）——它是机器卡的唯一收件箱，藏在折叠开关后面等于每一张雷达卡都可能没人看见；§51 hand lane 免批退役（D80.4，它唯一的喂料口就是被删掉的提案捕获框，owner 想直接开跑走 §34 `mode:"run"` 的直跑框，那条路本来就直接产 `approved`），§65 self_improve 免批**存活**并重锚到 `detected`（D80.5，§0 第 12 条的「唯一例外是 §65」一字不动，代价是 `dispatch.py` 里多一道 `policy.is_self_improve_sources` 守卫——没有它，「扫 `card_sent`」改成「扫 `detected`」就把整条潜在任务列变成自动派发的候选池）；`raising` 灰占位行随卡搬进同一条侧条（D80.6，「研究并提议」自此就地写厚而不再升级成提案）；§45 的 FULL / LIMITED 改判为**通知资格**（D80.7：FULL 落潜在任务**并**响通知，LIMITED 靠 add-only 字段 `quiet_birth` 安静落地，回声环的那一刀照旧可观测可判例）；§76.2 的 `decision_due` / `mention_escalated` 两个 bool 下到 `debt[]` 行（D80.8）；`alerts.py` 的通知 diff 从 `needs_approval[]` 改盯 `debt[]`（D80.9——不改的话每一条新卡与结算通知都**静默**死掉）；§34bis 的按钮退役但它驱动的通用 registry 写入护栏 / 起止快照 / 写入台账整套保留、重锚到一次普通直跑（D80.11，`tests/test_proposals_triage.py` 里测这半边的方法逐条改锚，不许删，覆盖是资产）；Dock / 壳角标 = `debt + needs_input + review`（D80.12）；store2 梯子 v2 → v3 只加 `transition_whitelist` 行、不碰任何一张卡（D80.15，§0 第 1 条：只有 actd 能转移卡）。

**三处刻意的偏离 / 边界**：① **`prev_status` 不写 `card_sent`（D80.10，偏离迁移惯例）**——`prev_status` 是回收站的**回程票**，照惯例原样保留就意味着一张被扔进回收站的提案卡在 `restore` 之后被送回一条已经退役的车道，正好是「可逆」的反面；改成归并扫描只追加一行带日期的 `notes`（`[<YYYY-MM-DD> §78] 提案车道退役，卡移入潜在任务（issue #447）`），由 `registry.restore` 把 `prev_status == card_sent` 钳到 `detected`。② **iOS 明确不在射程内（D80.14）**：`ios/` 一个字节不动，手机上仍然显示那一页已退役的提案列，手机发出的 `expected_status: "card_sent"` 会被 §32.2 的 stale-guard 判过期而诚实 no-op（不是静默吞）——明知且接受的代价，phone 半边另案排期，§78.10 把这条写进法里而不是留给下一个 session 猜。③ **`mac/Sources/` 不动（D80.13）**：原生 app 是 §66 的终版行为规格、不是在产的面，退役只由 `scripts/ui/extract_native_inventory.py` 的 `LANE_OWNER` 归属表表达（`needs_approval` → `owner: "retired"`，只列不判，照 D29/D30 给 `rail:order` 定下的先例），`parity_check._lanes_order_ok` 随之只比 gated 的列；`ui/parity/pending.txt` 与 `waivers.txt` 是 shrink-only，两份都零改动。
