**修法**：`scripts/auto-deploy.sh` 新 `session_gate`——CI 闸门与脏树检查之后、`merge --ff-only` 之前（以及 `install_incomplete` 的 install.sh 修补重跑之前）问一次 roster：新 `act.executor.live_session_count()` 复用 executor 既有的 `_roster_query` / `_parse_roster` / `_unwrap_roster`（同一个 §55 稳定副本 claude，`agents --json --all`，不另造 parser），数「`kind != interactive` 且带 `pid`」的条目——pid 就是「重启会打断的进程」这个谓词；state 不参与（事故里的 worker 就是 done + pid + owner attach 着），owner 终端里的 interactive 会话不算。N > 0 → `status=deferred` + add-only 键 `deferred_reason=sessions_running` / `deferred_sessions=N` / `deferred_since=<episode 首次>`，日志一行、不通知、HEAD 不动、exit 0；N = 0 放行并清键。**没有时间上限**：任何等待都不许变成 kill——永不结束的会话是 §46/#119 收割机制的事；连续满 `AUTODEPLOY_DEFER_WARN_AFTER`（6 h）后日志 WARN，doctor `auto-deploy` 行 OK → WARN「更新已就绪，等待 N 个会话结束已 X 小时」（`auto_deploy_row(state, now=…)` 时钟注入缝），web `DeployLabel` 次级色「新版本已就绪，等待 N 个会话结束后更新」→ 警告色 + 「（已 X 小时）」。roster 读不到 = fail closed：`deferred_reason=roster_unknown`、无 `deferred_sessions`、镜像私账 `roster_unknown_ticks` 计连续未知，满 `AUTODEPLOY_ROSTER_UNKNOWN_LIMIT`（3）后下一轮让行并说明；中间读到数字即清零。`--force` 跳过并记数。回滚不延后（几分钟前刚以 0 放行；doctor 刚判死的代码不能停在半路且没有可续路径），只在日志点名打断了几个会话。

**实证（一次性 launchd label，三种子进程形状，bootout 后清理）**：`launchctl bootout` 只 SIGTERM 该 job 自己 process group 里的进程；`setsid` 的直接子进程与 double-fork 的守护进程都活着。live 机器上 claude 的 worker（`bg-pty-host` / `bg-spare`）挂在 `claude daemon run`（自己的 session、ppid 1）之下、不在 actd 的进程组里；install.sh:502 与本脚本 run_with_timeout 的 `pkill -TERM -P` 只在看门狗超时才开火（那一轮 install.sh 跑了 2 m 15 s）。所以 bootout 本身不是直接的信号源；claude daemon 内部的路径从日志定不下来（daemon.log 05:35Z 无事件；会话转写 05:23Z 已完成本轮、05:26Z away_summary；05:42Z 三个会话与一个 spare 两秒内一起 settled，形状像 fleet 的 respawn 而非部署）。法条不依赖那个机制：不在活会话之下重启 actd（以及 install.sh 一并重启的 server / syncd / 壳 app relaunch、新 actd 首个 pass 的 reconcile）消掉的是整一类。任务里的第二个弱信号（稳定副本 2.1.259 vs 终端 2.1.261）在 05:34Z 的 install 日志里已不成立（`stable daemon claude … unchanged (2.1.263)`），未动。
