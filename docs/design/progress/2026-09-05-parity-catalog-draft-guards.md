law: §68.1 追记（草稿守则四条：同区刷新按键合并 / beforeunload 离页守卫 / 数字草稿非法即挡 / telemetry 联动禁用）

**背景**：审计比对 `mac/Sources/Settings.swift`（头注「NO deferred save」——开关改即落盘、文本框回车 / 失焦即提交、没有全局保存键）与 web `CatalogSection`（草稿 + 「保存」）发现三条 gap：`settings-save-semantics-draft-vs-immediate`（草稿没有离页守卫，且被同区即时写者的目录刷新整份清掉——实测在 `owner_slack_user_id` 里打字后勾一个频道，字就没了）、`settings-telemetry-cross-field-gating`（level / capture_input 不随总开关与级别禁用）、`settings-catalog-number-invalid-save`（负数 / 空 / 小数的 int 仍能点「保存」，server 的英文 400 直接进 toast；回收站天数丢了原生那句整数提示）。owner 决策取 (a)：保留草稿模型（§68.1 已立法的选择），修缺陷，不改回即时落盘。

**做了什么**（全部 client-only，`web/src/components/settings/`）：(1) `CatalogSection` 的目录指纹 effect 从「重置草稿」改成 `mergeDraft`——用 `useRef` 记上一次对齐时的 effective（草稿形），每键判「草稿 ≠ 上次 effective」= 用户改过 → 留草稿，否则跟新 effective；自己「保存」成功后草稿整份对齐回执（原生 commit 成功后显示值 = effective）。踩到一个 React 细节：`setState(updater)` 的 updater 可能延到下一帧才跑，闭包里直接读 `ref.current` 会拿到刚换新的值——先抓成常量再传。(2) `dirty.length > 0` 时挂 `beforeunload`（`preventDefault` + 非空 `returnValue`），存净 / 卸载即摘；rail、⌘1…⌘7、`/open` 都走 `route.navigate` = `location.assign` 整页导航，所以它就是路由离开守卫。诚实注：壳的 WKWebView 没有公开的 beforeunload 委托（私有 `_webView:runBeforeUnloadConfirmPanelWithMessage:`），壳内不弹、直接走；浏览器里有效。(3) 新模块 `draftRules.ts`（两条纯规则，CatalogSection 与 FieldControl 共用避免互相 import）：`isValidNumberDraft(kind, value)`（非负有限数；int 还须 `Number.isInteger`）与 `isGated(key, draft)`（telemetry 两条联动）。`CatalogSection` 据此算 `invalidKeys`：任一非法 → 「保存」禁用、该键不计「N 项未保存」也不进 PUT；`FieldControl` 的数字框校验句按 kind + key（`numberHint`）：number 用既有「请输入不小于 0 的数字，如 <default>」，`trash_retention_days` 用原生整句「请输入整数天数，如 60（0 = 永不自动清）」（Settings.swift:1727，清单 id `control:settings:copy:enter-a-whole-number-of-days-…`，role copy 不入门），其它 int 用整数通式。(4) `FieldControl` 加 `disabled` prop（与 `isBusy` 合成 `off`；外层 `.is-gated` 淡显标签与控件，来源章 / help 照常），`CatalogSection` 传 `isGated(field.key, draft)`——按草稿判不按 effective，只禁不改值（原生 persistTelemetry 切 level 也不动 capture_input 的存值）。

**判例**：新文件 `CatalogSectionDraftGuards.test.tsx`（防腐 #7 一行为一文件）：同区刷新留改过的键、应用没改的键；自己保存后对齐回执；`mergeDraft` 三态；beforeunload 只在脏时拦、存净 / 卸载即摘；telemetry 联动（草稿切 basic → capture 禁用且值不动；总开关关 → 两个都禁；快照里就是关的 → 进页即禁）；int 填 1.5 / 空 / number 填 -1 → 「保存」禁用 + 提示句，改合法后 PUT 只带合法键。`parity.test.tsx` 的 fill 遍给数字框填 `-1`，过去靶着批准区的「保存」收「已保存」——现在那颗按钮按法条禁用，「已保存」由 Slack 区（填 demo 的空文本框）照常收到；顺手暴露了 parity mock 回 `{}` 时 `draftOf(saved)` 会炸的边角，回执缺 `fields` 就只靠合并 effect。`ui/parity/report.json` 零变化（gated 849 / PRESENT 830 / MISSING 0），`pending.txt` / `waivers.txt` 零改动。Playwright golden 未重生成（demo seed 的 telemetry 开且 detailed，无禁用态；数字框值合法，无提示句——截图像素不变）。

**Review 后两处收口**（同 PR，新 commit）：(i) `mergeDraft` 同键冲突——Slack 区的 `slack_channels` 文本框与勾选器写同一个键：框里 `C1, C9` 未保存、勾 C2 落 `[C1, C2]`，首版留草稿 → 再「保存」PUT `C1, C9` 把刚落盘的 C2 静默撤回（vitest 实测第二次 PUT payload）。改成「草稿改过 **且** server 没动这个键」才留草稿，两边都动以 server 为准（与首版整份重置同向，只是收窄到那一个键）。(ii) `invalidKeys` 只计用户改过的键——server 读 config.yaml 不查 ≥0（`_coerce_number`），`retention_days: -5` 进页就是 -5，首版把它算非法锁住整区的「保存」（实测切一个无关开关：「1 项未保存」但按钮禁用）；现在没碰过的越界值原样显示（红字提示仍在）、不脏不进 PUT、不锁别的键，一碰它才挡。两处都进 `CatalogSectionDraftGuards.test.tsx`（老码下 4 条红）。
