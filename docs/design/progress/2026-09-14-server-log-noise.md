pr: `fix/server-log-noise`（issue #314；owner 决策 D54）
phase: 横切（运维可读性；§54.2 server 生命周期）
law: §54.2 追记（add-only，2026-09-14：`_Server.handle_error` / 访问日志时间戳 / 轮询采样 / 日志仍不删）

**病灶**：owner 机器上的 `~/Library/Logs/zelin-ai-assistant/server.launchd.log` 已 1.9 MB，其中 **101 段**完整 traceback 是同一个 `ConnectionResetError: [Errno 54] Connection reset by peer`。浏览器关 tab / 刷新时 keep-alive 连接被 reset 是正常现象，但异常抛在 `http/server.py handle_one_request` 读请求行时——在 Handler 之前，`server/app.py` `Handler._dispatch` 的 `except (BrokenPipeError, ConnectionResetError)` 够不着它，socketserver 的默认 `handle_error` 于是照打全栈（`git grep handle_error origin/main` = 0 命中，这个覆写从来没写过）。同一份日志的请求行还没有时间戳（`log_message` 写 `"%s - %s"`，把 `BaseHTTPRequestHandler` 自带的 `log_date_time_string` 丢了），对不上「我 14:34 点了哪个按钮、server 收到了什么」；而行数里 99% 是看板每 5 s 一次的 `/api/board` / `/api/health` 轮询。§54.2 本来就禁过这种 traceback 洪水（EADDRINUSE 那条：「KeepAlive 每 10 s 一段 traceback 就是 §55 审计 L3 那种 14 MB 孤儿日志」），只是这条路径从规则底下溜了过去。

**改法**（`server/app.py`，三件事各自可关可测）：(1) 新 `class _Server(ThreadingHTTPServer)`，`make_server` 起的是它（返回标注不变，子类照样是 `ThreadingHTTPServer`）；`handle_error` 只在 `sys.exc_info()[1]` 是 `BrokenPipeError` / `ConnectionResetError` / `ConnectionAbortedError` 时静默返回，其余一律 `super().handle_error()` 打完整 traceback——**没有空泛的 `except Exception`**，真崩溃仍要看得见（这是本 PR 唯一的真风险，判例用 `ValueError` 与 `OSError(EMFILE)` 各钉一条）。(2) `log_message` 经新的纯函数 `_access_line(address, text, now=None)` 写行，行首是本地 ISO 时间戳带偏移（`2026-09-14T14:34:05-0400`，可排序、跨时区可读）；它仍是这条访问行的唯一写者。(3) 新 `Handler.log_request`：`/api/board` 与 `/api/health`（query 不算数）的每条访问行过进程级 `_PollSampler`（`threading.Lock` + `{(path, code): (last_ts, suppressed)}`，窗口 300 s，`now` 由调用方注入 → 判例零 sleep）；**分桶键含状态码**——状态码一变立刻写（新桶没有 `last_ts`；状态变化是信号），只有窗口内的同 path 同码重复不写行，被吃掉的条数随窗口后第一条真写出去的行报出来（`"GET /api/board HTTP/1.1" 200 4096 (+57 suppressed in the last 300s)`）——**日志不做静默丢弃**（宪法第 3 条）。非轮询路径、以及状态码形状不明（`"-"` / None）的行一律逐条写；`ZAI_LOG_POLLS=1` 关采样 = issue 里要的「debug 档」。

**闸只吃 2xx/304 是不够的（reviewer 抓到的盲点，spec 与 skeptic 都漏了）**：owner 那份 11518 行的 `server.launchd.log` 里，**1549 行是一模一样的 `127.0.0.1 - "GET /api/board HTTP/1.1" 404 -`**——13.4% 的行、全部 `/api/board` 行的 27%，连续横跨 5578–10731 行（持续期，不是一次性 burst；5 s 一拍 ≈ 720 行/小时）。只掐 2xx/304 的话这段洪水一行不少地照写，issue 的 Expected 2「日志里 99% 是轮询」在这条路径上依然成立。所以分桶键取 `(path, code)` 而不是 `path`：错误不因采样而消失（每窗口至少一行、带被吃掉的条数，甚至多了「持续了多久」这条信息），状态变化也不会被延迟（新桶立刻写）。CONTRACT §54.2 的追记同一个 PR 里就按这条改写（原句「任何非 2xx/304 一律逐条写」→「同 path 同码的重复才进采样；状态码一变立刻写」），判例 `test_codes_are_independent_buckets` / `test_status_change_logs_immediately` / `test_repeated_same_error_is_sampled_with_a_count` 各钉一条。

**取舍**：owner 的 Expected 1 给了「静默或一行 debug」、Expected 2 给了「降为 debug 或采样」，两处都选了后者的对偶——server 只有 stderr 一个去处（launchd 把它接进 `server.launchd.log`），进程里没有日志级别这套东西，为一行噪音引进 `logging` 配置就是加一个子系统（防腐 #9：先找已有机制）；采样 + 把吃掉的条数报在下一行，砍掉 99% 的轮询行而日志不说谎。窗口选 300 s 而不是按条数：看板轮询是 5 s 一拍，按时间算出来的「每 5 分钟一行」在肉眼扫日志时是稳定的节律。**日志文件本身一个字节不删**——server 永不写第二份日志、永不删 / 轮转（§55 审计 L3、§68.4 `GET /api/logs/{name}` 同款纪律），既有的 1.9 MB 归 owner 自己处置；本 PR 只让它不再长。

**边界 / 没做**：`act/webui.py` 有同一个缺陷（同款 `ThreadingHTTPServer` + 无时间戳），刻意不动——它随原生 Mac app 一起退役（D3），改它等于给要删的代码做维护。不加日志轮转、不加 `logging` 模块、不改 launchd 模板的日志路径（§55 路径纪律不动）。生产机上要等 auto-deploy 从 `refused_dirty` 恢复才吃到这个修复。

**判例**：新文件 `tests/test_server_log_noise.py`（22 条：`make_server` 起的是 `_Server` / 三个连接类异常静默且 stdout+stderr 皆空 / `ValueError` 与 `OSError` 仍打全栈 / `_QUIET_CONN_ERRORS` 逐字钉三个 / 时间戳正则 + 注入时钟 / 采样器窗口与 suppressed 计数 + 每路径独立 + **每状态码独立分桶** + 默认窗口 300 s / `_quiet_candidate` 十一格真值表（含 `HTTPStatus` 枚举、404/500 进闸、`"-"` 不进闸）+ `_status_int` 的形状归一 / log_request 的首条写·重复吃·计数后缀·query 不绕闸·**状态变化立刻写**·**同一个错误重复被采样且带条数**·非轮询路径·env 关采样·枚举渲染成数字 / `ZAI_LOG_POLLS` 取值口径）。全部直接练模块级纯函数与 handler 方法——`tests/test_server_common.py` 在 import 期把 `Handler.log_message` 换成进程内全局 no-op，经真请求断言「有没有写出那一行」是测不准的。既有判例零改动。
