**病历**：生产机从 2026-09-04 起跑 v1.0.23，期间 main 发到 v1.0.98、领先 270 个 commit。原因链是两条规则互相否决：checkout 常驻 `release` 分支（钉 tag + 叠 ingest 的工作数据 commit，永不 push），而 `scripts/auto-deploy.sh` 只在 `main` 上运作（§56.5 首条）——`state/deploy_state.json` 从 `2026-09-05T03:06Z` 到 09-09 22:25Z 写了 **539 次** `refused_branch`。真正致命的不是「落后」，是**没有任何地方告诉用户更新链路是断的**：顶栏 `DeployLabel` 写着「不在 main，部署暂停」，而同一个页面的「一键更新」按钮点两次都回 200 并说「已触发自动部署——几分钟后这里的版本会变」（`server/about.py::install_now` 无条件 kickstart 完就回 `{"ok": true}`，`about` 载荷里根本没有部署状态；`installNow()` 只对 409 做分支处理）。后果：#306 的 `exec cd`、终端接管整链（R-285 / PR #246）、#214 的误铸 pr_red 卡——上游全修好了，生产机一个也没拿到。

**D55 的取舍**：owner 的原话是二选一（正式支持 release 模型，或把工作数据搬出 checkout），并明确「不能像现在这样两套规则互相否决」。代拍选后者。选项 (a) 要让后台任务在 live checkout 上跑 `rebase`——重写本地历史、可能留冲突中间态、还要与 §56.3 第 4 步的脏树拒绝打架，而那一步存在的理由恰恰是「工作数据不该住在代码 checkout 的 tracked 文件里」。`AUTODEPLOY_BRANCH`（D17 的 env 旋钮）不是答案也不承诺是：脚本把 `origin/$BRANCH` 当部署目标并要求本地能 ff 到它，本地 `release` 与 `origin/release` 分叉 → 第 1781 行「fast-forward … impossible (local BRANCH diverged?) — refusing」（owner 09-09 亲自验过）。本 PR 因此**不动部署脚本一行**，交付的是两件：把谎堵死，和把 SOP 写成文。

**server 半**：`act/lib/deploy_state.py` 立两个集合作唯一真源——`BLOCKING = {refused_branch, refused_dirty, blocked_tcc}`（提前 kickstart 一轮也清不掉，下一轮会以同样理由再拒）与 `POISONED = {failed, rolled_back, rollback_failed, ci_failed}`（kickstart 照跑，但 `failed_sha` 在 main 挪窝或 `--force` 之前不会被 `sha_is_poisoned` 放过）；`_auto_deploy_fix` 升为 public `auto_deploy_fix`，doctor 的 `auto-deploy` 行与新的 409 从此共用同一句修法。`server/about.py`：`snapshot(home, state_reader=…)` add-only 带 `deploy_state`——**请求时现读文件**，不是 actd 的看板投影（actd 死了 / launchd 被 TCC 拦着时投影正是陈的那一份，而这一行要回答的恰是「更新链路还活着吗」；`server/diagnostics.py` 读投影的那条路不动）；`install_now(payload, runner, platform, state_reader)` 先读后动：`BLOCKING` → 零 kickstart + 409 `CONFLICT`，`details = {reason:"deploy_refused", deploy_status, deploy_detail, fix, label}`；其余状态照旧 kickstart（不带 `-k`），回执 add-only 带上一轮的 `deploy_status` / `deploy_detail`。顺序上「agent 未加载」仍先判——那台机器根本不走自动部署，正确答案是原生非 Sparkle 的兜底（打开 release 页），不是 `deploy_refused`。reader 抛异常 = 当没有记录（宪法第 11 条），依赖方向 `server → act.lib` 走既有白名单（`analytics_ingest → act.lib.analytics` 的同一条）。

**web 半**：`DeployLabel` 导出 `statusLabel` / `deferredLabel` / `BLOCKING_STATUSES` / `POISONED_STATUSES`，关于页一律复用——顶栏与关于页永不各判一次（防腐 #10）。`AboutSection` 四条路：(1) `about.deploy_state.status` 属于 `BLOCKING` → 「一键更新」**一进页就禁用** + 「更新链路断着：<状态词> — <拒绝原文>」+ 怎么修；(2) 真点下去吃到 409 `deploy_refused` → **逐字同一句**，且绝不 `window.open` release 页、绝不出现「已触发」，并顺手重拉 `/api/about` 让按钮跟着灰掉；(3) 旧 409（details 里没有 `reason`，= agent 未加载）→ 原生兜底照旧；(4) kickstart 真发生时按上一轮的状态说话——`deferred` 换成「上一轮还在等：<`deferredLabel` 原句>。会话散了这里的版本才会变；等不及就 `--force`（它会打断这些会话）」（kickstart 不带 `--force`，§56.3 的会话闸门会原样再判一次——这正是 skeptic 指出的第二个假承诺），`POISONED` **整族**（不论有没有 `failed_sha`）都拿不到承诺，`ci_pending` / `install_incomplete` / `fetch_failed` / 未知状态的承诺仍成立、只补一句「（上一轮：<状态词>。）」。

**复审追加（2026-09-14，PR #336 review）**：第一版把 `POISONED` 的降级写成了「`POISONED` **且** `failed_sha` 非空」，那是条错的判据。`scripts/auto-deploy.sh` 写 `status=failed` 的五处里只有 `poison_pairs` 那两处附 `failed_sha`；分叉 checkout 的「fast-forward … impossible (local $BRANCH diverged?) — refusing」（第 1781 行，`detail=git merge --ff-only <sha> failed`）、卷探针失败、`symbolic-ref` 读不动、认不出 GitHub 远端这四处都不附——第一处正是 owner 09-09 用 `AUTODEPLOY_BRANCH=release` 打到的那面墙，也是本 PR 自己写进 `docs/TROUBLESHOOTING.md` 的那个结局，而**分叉是永久态**：按「有没有 sha」分叉，等于把 #309 那句谎原样留给最该说真话的那一路。修法两件：(1) `installNote` 改成 `POISONED_STATUSES.has(status)` 整族降级——有 sha 说「<sha7> 在 main 挪窝之前不会被重试」，没 sha 说「上一轮是<状态词>：<detail>——这一轮很可能同样倒在那里，版本变了才算数；先 `tail -40 …/auto-deploy.log`」；(2) 回执 add-only 再加 `deploy_failed_sha`（`server/about.py` 现读那一份，优先于 `about` 快照里的同名键——中毒的那一轮可能是页面载入之后才倒下的，快照答不上）。§68.6 追记第 3、4 条同步改写，`AboutSection.deployRefusal.test.tsx` 那条钉住旧行为的断言换成整族真值表 + 一条分叉 checkout 的组件判例，`tests/test_server_about_deploy_state.py` 多钉「中毒但没有 sha」这一形状。

**版本号（§56.1 追记）**：新 `web/src/version.ts` 的 `releaseVersion` / `aheadCommits` / `aheadNote` 是渲染层的唯一真源；关于页「版本」行变成 `v1.0.23` + 一句「本地领先 92 个提交，未发版」，顶栏部署小字变成 `v1.0.23`、`+N` 进 title。真源与比较一个字不动（心跳、install_report、`update_check.parse_version`、doctor `version` 行的盖章对账继续用整串 `X.Y.Z+N`——§56.3 第 9 步的逐字相等判据依赖它）。

**取舍与留白**：(a) 「怎么修」那句由 web 自己的 `text(zh,en)` 写（一进页那条路没有任何 server 字符串，把 409 的中文 `fix` 复制进 UI 才是第二套双语机制）；server 的 `details.fix` 仍在 envelope 里给 API 消费者与日志，且与 doctor 行同一句。(b) `deferred` **不**进 `BLOCKING`：kickstart 会真的重读一次 roster，会话刚散的人不该被按钮拦住——它只是拿不到「几分钟后版本会变」的承诺。(c) 「修好后等下一轮，或 `--force`」这样写是因为状态可能刚被清干净（陈状态的出口）。(d) 数据 commit 搬出 checkout 是 D55 选定的长期方向，但**不在本 PR**：那要动 ingest 的落盘路径，另开 issue；本 PR 只保证这件事再也藏不住，并把 owner 09-09 走过的手工 SOP 写进 `docs/TROUBLESHOOTING.md`（备份分支 + store2.db 备份 → `git rebase vX.Y.Z release`（实录 102 个 commit / 13 个文件 / 零冲突）→ `bash install.sh` → doctor 35 ok / 3 warn / 0 fail）。**代价**：本 PR 合进 main 也不会让生产机自动升级——它的 checkout 还不在 `main`，自动部署照旧拒绝；这一轮修的是可见性与 SOP。
