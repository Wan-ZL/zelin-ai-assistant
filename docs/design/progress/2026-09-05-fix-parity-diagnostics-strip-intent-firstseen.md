**为什么**：审计对照原生 Diagnostics.swift / DiagnosticsRules.swift 发现 web 诊断条丢了两条 anti-nag 行为。(1) 原生 `gmailCardEligible` 对 setup 类 reason（no_credentials / no_address）要「真实意愿信号」——用户碰过开关（overrides 里有 `gmail_enabled`）或凭证文件存在；Slack 的 `connect_failed` 只在 token 非空时出卡、`mcp_not_configured` 只在 secrets 文件存在时出卡。web 版（#188 落地时）把 `enabled` 当成 intent，而三源开关默认全开、雷达在空白机上如实报 no_credentials / mcp_not_configured——D25 验收路径的看板因此常驻两张卡，dismiss 只安静 7 天；那条「fresh user 零卡」判例靠 `enabled:false` 才过，判的根本不是这件事。§66 追记里「`enabled` 即 intent」那句与 §48.4 正文（「enabled 默认 true」本身不是 intent）直接相悖。(2) 原生 `pruneFirstSeen(keeping: liveSignatures)` 每次重建都把不再活着的签名从首见台账里忘掉；web 的 `diagnosticsFirstSeen` 只增不删——录制关几天再开，几天前的时间戳让 vault_empty 立刻告警，35 min 预热只在有生之年的第一次有效。

**做了什么**：意愿信号搬进 actd 投影（web 没有文件系统，§44 单写者，server 只读转发）：`act/lib/dashboard._source_signals` 给每源条目追加 add-only 两键。`intent` = overrides 里存在 `<src>_enabled` / 嵌套 `features.<src>_radar` / 平铺 `"features.<src>_radar"` / 手写 `<src>: {enabled}` 任一（config `_apply_settings_overrides` 认的拼法都算，开或关都算碰过）∨ §19 凭证文件存在（空文件 = 配到一半）∨ 凭证非空；obsidian 的「配到一半」= `obsidian_raw` 指定过。`secret_present` = §19 凭证非空——**与雷达同一套三层解析**（`config/secrets/<name>` → config.yaml 显式路径 → 旧默认路径 `~/Desktop/Keys`）；obsidian 恒 false。坏 overrides / 探针异常 → 两键 false，投影不崩。web `DiagnosticsStrip` 导出 `gmailCardEligible` / `slackCardEligible`（原生逐条：setup 类要 `intent !== false`、`disabled` 永不出卡；Slack token 类要 `secret_present !== false`、`mcp_not_configured` 要 `intent !== false`），键缺席 = 旧 payload = 老判据；`agent_missing` 不看信号、让位规则不变。首见台账：导出纯函数 `pruneFirstSeen(seen, live)`，组件在遍历完 `buildDiagnosticCards` 的全部结果（预热 / dismiss 之前）后修剪再落 localStorage，无变化返回同一对象。`types.ts RadarSourceHealth` add-only 两键。golden `tests/fixtures/dashboard_golden.json` 随 add-only 键**刻意重铸**（fixture 里 gmail 碰过开关无凭证 → intent 真 / secret 假，slack 有 token → 双真，obsidian 双假；overrides 与 secrets 目录都钉进 fixture 的 state_dir，不吃共享沙箱）。CONTRACT §48.4 追记一段；§66 追记那句只加修正注不删字。

**review 修正（同日，PR #241 needs_fix 两条）**：(1) 初稿的 `secret_present` 只看 §19 前两层、不读旧默认路径（理由是原生 `SecretsIO.hasSecret` 也只看 config/secrets）——reviewer 在临时 HOME 上复现：token 只在 `~/Desktop/Keys/slack-user-token.txt`（§19 明文保活、秘钥页也算「使用旧路径」在场的那层），`radar_slack.get_token` 解析到它、Slack 拒绝、雷达写 `connect_failed`（那条分支只在解析到 token 后可达），投影却出 `secret_present:false` → web 的 `slackCardEligible` 把主干上可见的「Slack token 无效」卡藏掉；gmail 旧路径应用密码 + 没填地址 → `no_address` 同样被藏。修法取 reviewer 的第一方案：信号与雷达同一套三层解析——旧默认路径进单源表 `act/lib/secrets.LEGACY_DEFAULT_PATHS`（`radar_slack.DEFAULT_TOKEN_PATH` / `radar_gmail.DEFAULT_APP_PASSWORD_PATH` 自此从表里取），投影经 `secrets.read_path` 探它、不响弃用告警；Config 类缺省值不算显式路径（gmail 的缺省字面就是旧路径，由表兜、同一文件只探一次）；判例 patch 这张表进沙箱（tests/__init__.py 不沙箱 `~`，开发机真凭证绝不能成为判例输入——初稿那条「缺省旧路径从不被读」的判例正是为此，现在换成「不探 Config 缺省字面、只经表探一次」）。web 资格判据零改动。(2) `_switch_touched` 的拼法表与 config 真认的对齐：加点式 `sources.<src>_enabled`（`_override_sources_key` 认、此前漏算），嵌套 `<src>: {enabled}` 只算 gmail（`_OVERRIDE_HANDLERS` 只有 gmail 的处理器，`slack: {enabled}` 对 config 无效、初稿误算成碰过）；判例同时断言 config.load_config 的真实结果，拼法表与 config 不许再漂。CONTRACT §48.4 追记一段修正（add-only，不改上段字）。
