**病灶**：PR #330（R-214）查到了 2026-09-07 live 事故的完整取证链，并明说把修法留给「另一张卡」——就是本 PR。`mac/package.sh` 写进 .pkg 的 postinstall 无条件把 root 属主的管线母本 `rsync -a`（无 `--delete`、无任何目的地判据，excludes 只护 `config.yaml` / `config/secrets/` / `state/`）进 `$USER_HOME/Projects/zelin-ai-assistant`，再跑 `install.sh --pkg-postinstall` 重启守护进程。这台机器上 `~/Projects` 是指向 `/Volumes/Storage/Server/Projects` 的符号链接，那底下就是 live 开发 checkout。2026-09-07 21:59 PDT，**退役的** `Zelin's AI Assistant (old).app` 里的 Sparkle（`SUEnableAutomaticChecks` / `SUAutomaticallyUpdate` 都是 true）自动下载并安装了 **v1.0.14** 的 .pkg（`/var/log/install.log` 的 Current Path 指向那个 bundle 的 `Autoupdate`；pkgutil 收据 1.0.14）：232 个 tracked 文件被改写成**更旧**的 tag 的字节（mtime 齐刷刷是 v1.0.14 的 commit 时间 = `git archive` 的章经 `rsync -a` 原样带过来），18 个上游早已删掉的源码文件作为 untracked 复活（`web/src/pages/AskPage.tsx` import 的函数在 main 的 `api.ts` 里不存在 → `ui` 步 `tsc` 必红 → 部署回滚），actd 被重启后把 #214 早已修好的 `_ci_red` 旧判法钉回内存——09-08 起每天一张 `pr_red`，其中 #282 / #291 / #320 / #324 四张是假卡，R-201 / R-203 / R-211 / R-214 四个 session 各烧一遍同一个非 bug。自动部署自此 `refused_dirty`，`last_deployed` 冻在 09-07 11:09Z。

**改法（三件事，各自可测）**：(1) 新 `mac/scripts/pkg_dest_guard.sh` —— 唯一实现的判据：目的地用 `cd … && pwd -P` 逐层解开符号链接（不存在的尾巴接回解析出的祖先，「还没建出来的目的地」也判得动），然后从它自己一路往上走到 `/`，任何一级有 `.git`（目录或 worktree 的 gitdir 文件）就 **exit 3**，stdout 给出那棵 checkout 的根、stderr 给人话与修法。走到 `/` 而不是停在 `$HOME`：事故里的 checkout 在 `/Volumes/Storage/…`，停在 `$HOME` 的守卫在真实形状上等于没装（代价——把 `$HOME` 本身做成仓库的 dotfiles 机器会被拒——写进 §74.1）。(2) 两处闸都 **fail-closed**：postinstall 在 `mkdir`/`rsync` 之前问一次，命中（或守卫缺席时 bash 的 127）= 整段 per-user setup 跳过——不拷贝、不跑 install.sh、不重启守护进程、不 `open` 旧 app，退出码仍是 0（两个 payload 确实装好了，报「安装失败」只会诱使用户再装一次）；`install.sh --pkg-postinstall` 在 flag 解析之后、任何副作用之前再判一次 `$REPO_ROOT`，命中 = exit 3、`$HOME` 下零文件、不写 §23 报告（它防的是守卫出生之前打出来的旧载荷——那种载荷会把自己那份旧 install.sh 一起 rsync 进来）。交互模式与 `--non-interactive` 不受影响：checkout 正是它们该跑的地方。(3) **给退役 app 断粮**：装了守卫只缩小爆炸半径，发起端是那套还在每天自检更新的 Sparkle。`release.yml` 改发**零 `<item>` 的终止版 appcast**（对 Sparkle = 「你永远是最新版」），`sign_update` 签名步与它的 SUPublicEDKey 前置门随之下线（没有 enclosure 可签，留着只会让一次 secret 轮换无故拦下发版；`scripts/sparkle_pubkey.py` 与 vendor 的 `sign_update` 保留作重新武装的工具），`mac/Info.plist` 的 `SUEnableAutomaticChecks` / `SUAutomaticallyUpdate` 出厂改 false（下次构建旧 bundle 时生效）。

**取舍（issue 给了四个方案，owner 让挑）**：不做**版本比较**——「不许降级」是更弱的法条，它仍放行一个**更新**的 .pkg 覆盖工作树，而那里未 commit 的改动、不在 main 的分支、正在跑的实验照样被抹平；判据该是「这是不是一棵工作树」。不做 **`.pkg-managed` 标记文件**——`.git` 已经在那儿而且更准，再养一份会漂移、还会被 rsync 自己带进带出的状态是给自己加债（防腐 #4）。断粮取「终止版 feed」而不是「删掉 appcast 资产」——删了资产 = `/releases/latest/download/appcast.xml` 404，客户端每天重试并把它记成「链路坏了」；零条目的合法 feed 是「已是最新，永远」（宪法第 3 条）。**不代拍**从 `/Applications` 删 `(old).app`：D3 owner 原话是「等弄完之后，我明确让你把老的删掉，你再删掉」；本轮只保证它够不着新的 .pkg。已安装 bundle 的 Info.plist 一个字节不改（签名封条内，改了 TCC 授权就名存实亡，§54 同款理由）。

**判例** `tests/integration/test_pkg_postinstall_git_guard.py`（6 条，单文件预算 60 s，实测 ~3 s）：postinstall 的文本**逐字**从 `mac/package.sh` 的 `POSTINSTALL` heredoc 里取出——只重写 `MASTER=` 一行指向临时载荷，且那一行的字面被断言钉住（package.sh 改了形状就在这里红），系统工具（stat / dscl / sudo / id / launchctl / open）全是记 argv 的桩，PATH 够不到 `/usr/bin`，rsync 是真的。钉死四件事：目的地是 checkout → 拒且它的字节一个不变、install.sh 没跑、旧 app 没启动；经符号链接进 checkout（live 形状）→ 拒；守卫从载荷里消失 → 拒（fail-closed，不是放行）；空目的地 → 照旧播种并跑 `install.sh --pkg-postinstall`。另有 §74.2 的两条：真 `install.sh --pkg-postinstall` 在一棵有 `.git` 的临时树上 exit 3 且 `$HOME`、`state/`、`config/` 全空；以及闸的位置在任何写动作之前。**反向验证**：把 `mac/package.sh` 换回 `origin/dev` 的版本，这个文件 6 条里红 3 条。

**生效时机**：守卫随下一个 .pkg 生效，终止版 feed 随下一个 release 生效；**生产机上那份已装的 `(old).app` 仍是旧 Info.plist（自动更新 true）**，它下一次检查更新时读到的就是终止版 feed（所以这条路自下个 release 起真正断掉）。live checkout 里已经被回退的文件与 18 个残留 untracked 文件不属于本 PR 的射程（`docs/TROUBLESHOOTING.md` 新增一节写了怎么收拾）。
