三笔现成的工程遗产（直接抵掉 v1 风险项）

  1. headless 认证已解：cron 的 daemon session 读不了 Keychain OAuth → 你已用 ANTHROPIC_API_KEY 环境变量方案（key 放 ~/.config/，因为 cron 的 FDA 覆盖 ~/Documents 不覆盖 ~/Desktop）。雷达定时器照抄。
  2. TCC 地雷图已画好：launchd 读不了 ~/Documents（所以你从 launchd watcher 切到了 cron-chain）——新组件不再重踩。
  3. 防并发/增量/日志模式：lockfile + stale 检测、marker 文件、/tmp 日志——雷达和执行器直接复用同一套。
⚠️ 遗留待验：Slack/Atlassian MCP 的 OAuth 在 cron 下是否可用（与 ANTHROPIC_API_KEY 是两回事）。v1 首跑验证；兜底 = Keys 里的 Atlassian API token + Slack 改发通知的备用通道。

claude agents 调研（点 2）

它是什么：官方后台会话仪表盘（TUI，v2.1.139+，research preview）。分组显示 Pinned / Ready for review / Needs input / Working / Completed；支持派发新任务、attach 进会话、stop/respawn。--dangerously-skip-permissions 的作用是让从这个面板派发的会话免权限确认（等价 bypassPermissions）。
你关心的结论
能看到什么claude --bg 启动的后台会话、背景化的 shell 任务、/loop 循环。状态含 needs input（等你回复或等权限）——正是你要的"需要我输入的东西"。不含 subagents 和 cron 任务。
程序化读取✅ claude agents --json（state = working/blocked/done/failed/stopped + waitingFor 字段）；文件级 ~/.claude/daemon/roster.json + 各 job 的 state.json 可被 fswatch 监听
对产品的意义执行层不自建：执行器 = 用 claude --bg 派任务（自动 worktree 隔离）；状态监控不自建：轮询 --json；Mac 查看面 v0 现成：你直接开 claude agents TUI
仍要自建①雷达+注册表（它不管需求从哪来）②审批流（它没有远程审批——blocked 会话只能本机回复）③手机通知回传（监控脚本发现 needs-input/completed → Slack DM 你）④菜单栏计数（SwiftBar 读 --json，Level 1 一小时能做出来）

Anthropic 式 review 到底是什么（点 4）

直接回答你：你那种"试一下功能有没有弄出来、能不能跑"，在 Anthropic 的体系里是一层正式的 review，学名"行为验证"。Erik Schluntz（Anthropic 研究员、agents 负责人之一）原话："Instead of asking 'Is this code good?', ask 'Does this system behave correctly?'"，以及 "When doing vibe coding, the only code I usually look at is the test code. Only when the tests pass do I feel confident."——他也不逐行读实现。Boris Cherny（Claude Code 作者）同样不逐行读，前端改动让 Claude 自己开浏览器截图对比迭代到对为止。你的直觉不是偷懒，是他们也在用的方法。
但关键区别：Anthropic 从不让"跑一下"做唯一的一层。他们的 review 是五层防线，人只出现在最后两层的高风险处：
层做法证据
1 · 可运行的验证器每个任务先给 Claude 测试/构建/截图对比，"If you can't verify it, don't ship it"官方 best practices 第一条；Boris："有验证回路质量 2-3x"
2 · 自动 AI 审查（合并门禁）所有进 codebase 的改动先过自动 Claude reviewer（bug/安全/缺陷）官方披露：能拦下 claude.ai 历史事故背后约 1/3 的 bug；2026-05 起其生产代码 80%+ 由 Claude 编写
3 · fresh-context AI 互审合并前用干净上下文的第二个 Claude 审 diff（"不会偏袒自己刚写的代码"）官方 best practices 的 Writer/Reviewer 模式
4 · 人审——按风险分级生产合并仍有 human in the loop，但人只深入核心逻辑/强观点处；人审已被官方称为"新瓶颈"Boris（Latent Space）；著名的一天合 22,000 行 RL 代码案例：改动限定叶子节点 + 核心逻辑仍严格人审 + 离线无安全风险才敢做
5 · Dogfooding + 灰度内部一天发多版、feature flag 灰度、soak period也失灵过：2026 年 3-4 月质量回退一个多月才定位，postmortem 的整改是加灰度和评测——不是加逐行人审
"第二天 ship"的速度来源：并行 agent（Boris 一天 20-30 个 PR，5 个并行实例）、前置规划换一次成型（"once there is a good plan, it will one-shot almost every time"）、自动验证回路（人不再是每个错误的发现者）、小步+可回滚（撤回便宜所以敢快）。不是"不 review"，是把 review 从人逐行读改造成"机器和第二个 AI 先筛，人只看刀刃"。
落到你身上（= Assistant 质量门的出处）：①每个任务给执行器一个可运行检查，要它交证据；②你只花 5 分钟读测试断言是不是真需求，不读实现；③合并前 fresh-context 子代理审 diff（一条命令的成本）；④按风险分级——内部只读工具试功能即可合，碰生产数据/不可逆/凭证的那一小块核心才人肉读；⑤draft PR + git checkpoint 让撤回便宜。

回 Arash 的弹药：Anthropic 语境的 next-day ship = 前置规划 + 自动化验证兜底 + 小爆炸半径 + 人审只盯核心——他们自己也为速度交过一个月的学费，整改方向是加灰度评测而非加人审。你要对齐的是这套系统，而不是"更拼"。（来源：anthropic.com "When AI builds itself"、Claude Code best practices、April 23 postmortem、Boris Cherny 访谈 ×3、Erik Schluntz "Vibe coding in prod"）

顺毛 Arash SOP（点 3）

核心洞察（来自画像的全部证据）：他的不满几乎从不来自"活不够好"，而来自"看不见"。他所有的催促都发生在下达后 24h 无回音的窗口里；他最痛的抱怨是"讨论看起来 aligned 但没落成 action item"；他重复提第二遍的事全是第一次没收到闭环信号的。反过来，他对准备充分的 draft 秒批、对坦诚的 postmortem 明确欣赏、当面夸过 "really good design, actually. Honestly."——活本身他是认可的。

所以"顺毛"的正确姿势不是加班干更多活，而是把"可见性劳动"外包给 AI：让他在每个他习惯性检查的时点，都发现你已经在那里了。你的时间只花在两处：点 ✅，和真正的工程。

七件全自动的可见性劳动（Assistant 的 arash 模块）

#自动动作对应他的哪根毛
1每条新 directive 24h 内 ack 草稿（"captured, plan by 周X"）——你过目后发他的实测催办窗口 <24h（5/27→5/28 "any update?"）；ack 一到，催促消失
2会后 2h action-item 清单草稿（发他确认）直击 7/1 抱怨"讨论不落 action item"；还制造他喜欢的 documentation
3交付模板自动带 delta + cost + insight→decision 三行"share the delta" / "Let me know the cost" / "这样才是 data-driven"——全是他原话
41:1 前一天自动生成 ready/not-ready 清单 + 双向欠账清单（含他欠你的：doc、dedicated engineer、hire）他教过："define priorities... come back and say this is ready, this is not ready"；他也期待被 remind
5大额消耗当天主动附产出说明他盯 Redash、追过 $18-19K 账单——抢在 telemetry 追问之前
6standing artifacts 自动维护：training log、system card per ckpt、R&D weekly page他说一次就算数且会复查（system card 催过 ×2）；这三件流程债自动清零
7deadline 前 1-2 天自动 progress-delta 报告草稿他的 deadline 语义 = "届时要有 tangible progress"，不是要完美（"two quarters is fine"的前提是过程可见）
两条人工纪律（AI 替不了）：① 分歧要显式对齐，不能静默处理——structured-output 之争、Raja 分工都属于"待他拍板"，卡片会单独标色；② 语气≠严重性——"Good work!" 开头的消息照样可能全是整改项，判级看词典（"needs to be fixed" vs "you may want to consider"），别看表情。
